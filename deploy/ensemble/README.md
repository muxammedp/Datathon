# Экспериментальный ансамбль ForteVision

Отдельный серверный эксперимент: трекер людей + видеокодировщик действий + два визуальных специалиста + обучаемое объединение оценок. Сайт и старое обучение InternVideo этим модулем не изменяются. Качество ансамбля на банковских видео ещё нужно измерить; 85% не заявлены.

Фактические локальные проверки: [VALIDATION.md](VALIDATION.md).

## Компоненты

| Компонент | Задача | Что обучается на наших данных |
|---|---|---|
| YOLO11n + ByteTrack | Детекция людей и временные ID внутри одного ролика | Ничего; лица не распознаются |
| Microsoft X-CLIP base patch32 | Признаки движения в коротких последовательностях полного кадра и, если задана, кассовой области | Маленький регуляризованный бинарный классификатор поверх замороженных признаков |
| Qwen3-VL-8B-Instruct, контекст | Наблюдения о взаимодействии, видимых действиях и продолжении обслуживания | Исходные веса заморожены |
| Та же Qwen, касса | Отдельный запрос о видимом пересчёте, передаче и обращении с наличными | Исходные веса заморожены |
| Итоговый классификатор | Совместная оценка сигналов действий, контекста и наличных | Логистическая регрессия на шести признаках |

Это три набора исходных весов, а не четыре одновременно загруженные большие модели. Два запроса Qwen используют общие веса, поэтому их ошибки могут коррелировать. Детектор сообщает геометрию и ID специалистам; итоговый классификатор получает оценки X-CLIP и двух запросов Qwen. Наличие ансамбля само по себе не гарантирует улучшение.

Веса фиксированы ревизиями и SHA-256 в `model-manifest.json`. Скачивание обращается только за публичными файлами моделей. Во время обработки модели работают на вашей машине; никаких запросов к внешним AI API нет. Видео, кадры, признаки и результаты остаются локальными и не включаются в Git или исходный ZIP.

## Brev: установка и запуск

Используется отдельная `.venv`. Python 3.10+; предпочтительно уже установленный на сервере Python 3.12. Расчётная целевая машина — имеющаяся L40S 48 GB, 32 GB RAM. Совместная обработка полного Qwen 8B на этой машине ещё не измерена. Исходные файлы моделей занимают около 18.3 GB, дополнительно нужны зависимости, видео и кэш кадров. При установке оставьте хотя бы 40 GB свободного места.

Сначала завершите или остановите текущее обучение в его терминале: два тяжёлых процесса на одной GPU не запускайте. Старые результаты сохраняются.

```bash
cd ~/Datathon
git pull --ff-only
cd deploy/ensemble
bash setup.sh
```

Проверка доступности GPU и установка выполняются один раз. Успешная установка ещё не означает, что модель обучена.

Извлечение признаков всех 40 уникальных видео и последующее обучение объединения:

```bash
.venv/bin/python run.py --dataset ../internvideo/open-dataset --output results/features-v1
.venv/bin/python fusion.py --dataset ../internvideo/open-dataset --cache results/features-v1 --output results/fusion-v1
cat results/fusion-v1/summary.json
```

Если среда подключена к `~/forte-internvideo` через существующие символические ссылки, путь `../internvideo/open-dataset` уже ведёт к данным. Скрипт проверяет исходные SHA-256, а имена файлов не использует как признаки. Для первого пробного прогона можно отдельно обработать один ролик: `run.py --video /полный/путь/ролик.mov --output results/smoke-v1`. Не смешивайте пробный кэш и кэш полного обучения без понимания их состава.

Стадии: `media_ready` → `action_ready` → `qwen_window` / `qwen_ready` → `extraction_complete`. Извлечение выполняет модели по очереди, чтобы освобождать GPU. После этого `fusion.py` обучает небольшие классификаторы на CPU и выводит пять `fusion_fold_complete`. Веса Qwen и X-CLIP в этой версии не дообучаются.

Повтор той же команды продолжает вычисления по проверенному кэшу. Если изменились код, модели или параметры, используйте новое имя каталога, например `features-v2`; старые результаты не перезаписывайте. Ошибка специалиста не превращается в «нарушений нет». После аварийного завершения файл `.ensemble.lock` можно удалить только убедившись, что соответствующий процесс уже остановлен.

## Пакетная обработка Qwen

Первый вариант `run.py` делает четыре последовательных вызова Qwen на окно: оценка контекста, наблюдения контекста, оценка наличных, наблюдения наличных. Генерация JSON идёт токен за токеном, поэтому время меняется вместе с длиной ответа. Старые строки `qwen_window.elapsed_sec` показывают накопленное время **внутри ролика**, включая первую загрузку модели; это не длительность отдельного окна.

`run_batched.py` объединяет две оценки в один пакет и два ответа в другой пакет. Остаются те же веса, запросы, выбранные кадры, ограниченная память и лимит 384 токена на каждый ответ. Новые логи отдельно показывают загрузку модели, длительность окна `elapsed_sec`, накопленное время `video_elapsed_sec`, время оценок/генерации и число токенов. На одном фрагменте пользователь измерил на L40S 29.12 s последовательно и 25.29 s пакетно; это не измерение полного видео. Текущая версия пакетного протокола — `forte_specialists_batched_v2`, с исправленной обработкой списков событий.

Текущий последовательный запуск можно завершить и получить исходную точность. Обновление не меняет файлы, входящие в его fingerprint. Не запускайте сравнение одновременно с ним: результаты времени будут искажены, а две копии Qwen займут дополнительную память. После освобождения GPU выполните локальное сравнение одного окна:

```bash
cd ~/Datathon && git pull --ff-only && cd deploy/ensemble
.venv/bin/python benchmark_qwen.py --cache results/features-v1 --output results/qwen-batch-benchmark.json
```

Модель загружается один раз. Две пары запусков чередуют порядок последовательного и пакетного режима, используют одинаковое первое окно и пустую предыдущую память. Числовой отчёт показывает время, пик выделенной GPU-памяти, разницу оценок и совпадение наблюдений; кадры и текст наблюдений не экспортируются. Проверка SHA весов и первоначальная загрузка показываются отдельно. Это небольшой замер, не проверка точности и не время полного видео. Повторный отчёт сохраняйте под новым именем.

Если пакетный режим быстрее и укладывается в память, полный эксперимент запускается в новом каталоге:

```bash
.venv/bin/python run_batched.py --dataset ../internvideo/open-dataset --reuse-from results/features-v1 --output results/features-batched-v2
.venv/bin/python fusion.py --dataset ../internvideo/open-dataset --cache results/features-batched-v2 --output results/fusion-batched-v2
```

`--reuse-from` копирует только совместимые проверенные кадры/треки и признаки X-CLIP. Старые результаты сохраняются. **Qwen пересчитывается**: округления BF16 при пакетном выполнении могут изменить наблюдения и последующую память, поэтому смешивать старые и новые оценки нельзя. Повтор той же пакетной команды продолжает собственный кэш. Коэффициенты объединения обучаются на новом кэше, а `predict.py` автоматически выбирает соответствующий способ извлечения по протоколу классификатора. Новых весов и переустановки среды для пакетного режима не требуется.

Если замер показывает `invalid_json_or_schema`, числовые оценки были получены, но структурированные наблюдения не приняты. Причина может быть в JSON-оформлении или несоответствии полей, ID и таймкодов. Не считайте совпадение двух пустых запасных ответов подтверждением качества. Для определения причины на одном окне, при свободной GPU:

```bash
.venv/bin/python diagnose_qwen.py --cache results/features-v1 --output results/qwen-diagnostic-v2.json --require-valid
```

Диагностика выводит только фиксированные коды причин и структурные сведения. Текст ответов, кадры и значения событий в отчёт не попадают. Проверка снятия внешних Markdown-ограждений служит только диагностикой: правила принятия наблюдений и прежний кэш не изменяются.

В `observations_v2` проверяются и сохраняются все элементы списка до 64 событий. Прежний валидатор отклонял весь ответ при списке длиннее восьми. Также принимается один объект события с точными полями `kind`, `time_sec`, `track_ids`, преобразованный в список из одного элемента. Неизвестные ID, неверные таймкоды, категории, лишние поля, произвольные словари и `null` по-прежнему отклоняются. События не обрезаются до восьми; только память следующего окна ограничена восемью последними наблюдениями. Запрос по-прежнему просит компактный ответ и не увеличивает число генерируемых токенов. Это исправление приёма наблюдений, не доказательство правильности их содержания.

`--require-valid` сохраняет отчёт и завершает команду с кодом 2, если хотя бы один специалист не прошёл проверку. Можно соединить эту команду с извлечением через `&&`: полный набор начнёт обрабатываться только после успешной проверки первого фрагмента. Это проверка схемы одного окна; остальные окна и точность требуют собственного контроля. Старая пакетная версия имеет иной fingerprint и не смешивается с v2; используйте новые каталоги `features-batched-v2` и `fusion-batched-v2`. Исходный последовательный кэш `features-v1` остаётся совместим со своим старым запуском.

## Проверка нового ролика

```bash
.venv/bin/python predict.py --video /полный/путь/new.mov --bundle results/fusion-v1/fold-0/predictor.json --cache results/predict-v1 --output results/new-video.json
```

`fold-0` выбран заранее, а не по лучшему тестовому результату. Этот классификатор обучен на 24 роликах, порог выбран на 8 других; остальные 8 использованы для проверки. JSON сохраняет коэффициенты и необходимый протокол; для переноса нужны этот файл, соответствующий исходный код и скачанные базовые веса. Файлы `.pt` старого InternVideo в этот ансамбль не подключаются.

У `predict.py` общий лимит 300 секунд: зависший/слишком долгий дочерний процесс останавливается, возвращается явная ошибка обработки. Это ограничение времени выполнения, **не доказательство**, что модель успевает успешно проверить 145-секундный ролик за пять минут. Скорость на L40S надо проверить на новом полном видео; загрузка весов и проверка хешей входят в запуск. Обработка набора для обучения не имеет лимита в пять минут на весь набор.

`candidate_evidence` содержит конкретный выбранный кадр, его индекс, приблизительный таймкод и интервал для просмотра. Это кандидат для проверки: точность определения момента нарушения ещё не измерена. Выбор сделан по оценке действий и наблюдению Qwen либо середине окна. Нельзя выдавать этот кандидат за подтверждённый кадр нарушения. CLI JSON не является финальной схемой API жюри.

## Покрытие, память и новый ракурс

Весь исходный файл декодируется последовательно. Модели получают выбранные кадры с частотой 4 FPS в окнах 16 секунд с перекрытием 4 секунды. Нет общего ограничения «120 кадров на всё видео»: число окон растёт с длительностью. Короткое действие между выбранными кадрами всё ещё может быть пропущено.

X-CLIP обрабатывает все выбранные кадры короткими блоками по 8 кадров с шагом 4. Последний блок дополняется последним кадром при необходимости. Изображение вписывается в квадрат с сохранением пропорций вместо растяжения портретного кадра; это отличается от стандартного центрального кропа модели и требует проверки качества.

Qwen получает до 16 кадров каждого окна с таймкодами, координатами людей и до восьми прошлых наблюдений. Это последовательность изображений, не native-video вход Qwen. Память ограничена: передаются только структурированные наблюдения из предшествующих окон, они не считаются подтверждённой истиной. Внутри одного ролика ByteTrack сохраняет ID, но возможны потери и перестановки ID. Исчезновение ID не считается уходом кассира.

По умолчанию роли неизвестны. `camera.example.json` позволяет задать `cashier_zone` и `counter_crop` нормированными координатами `[x1,y1,x2,y2]`. Зона даёт только кандидата в кассиры, не достоверную идентификацию. При смене ракурса прежние координаты переносить нельзя. Основной запуск использует полный кадр без фиксированных зон, что исключает привязку к координатам старой камеры; устойчивость к новому ракурсу всё равно не доказана. Конфигурацию камеры фиксируйте до извлечения обучающего кэша и передавайте через `--camera`.

Если классификатор обучался с настроенными зонами, `predict.py` требует `--same-camera`: этот флаг уместен только при неизменившемся ракурсе. Для другого ракурса используйте классификатор полного кадра без настроенных зон.

Неизвестная активность, спорные роли и расхождение оценок сохраняются в причинах для проверки. Дополнительно считается эвристическое расстояние признаков до обучающих видео. Новый ракурс тоже может увеличить его; оно не устанавливает новый тип нарушения. Флаги неопределённости не превращаются автоматически в нарушение и не скрывают ошибки из метрик. Категории нарушений и нормативные ссылки модель в этой версии не выдаёт: таких целевых меток нет в таблице.

## Как проверяется обучение

Пять разбиений по SHA-уникальным видео: 24 обучение, 8 калибровка, 8 проверка. Все окна одного видео остаются вместе. В нормальных обучающих роликах используются все окна; в положительных — окна, содержащие размеченный момент. Такое слабое обучение не делает каждый кадр окна нарушением.

Для итогового классификатора оценки обучающей модели действий формируются ещё на трёх внутренних разбиениях. Он не учится на оценках, полученных от модели, уже обученной на том же ролике. Нормализация и коэффициенты обучаются только на обучающей части. Порог выбирается только на калибровочной части: минимальная сбалансированная ошибка при recall >= 0.5; это ограничение калибровки, а не обещание тестового recall. Гиперпараметры фиксированы до оценки.

`summary.json` сравнивает ансамбль с каждым компонентом на одних и тех же отложенных видео, считает ложные тревоги и пропуски. Пять сохранённых классификаторов нельзя объединять для повторной оценки этих же 40 роликов: четыре из них уже могли использовать конкретный тестовый ролик в обучении или калибровке. Набор многократно использовался в разработке, поэтому даже корректная перекрёстная проверка не заменяет независимый новый тест.

`candidate_window_hit_recall` дополнительно считает долю положительных видео, на которых модель и выдала положительный ответ, и выбрала окно с размеченным моментом. Это попадание в интервал, а не доказательство точности конкретного кадра.
