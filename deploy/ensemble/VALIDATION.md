# Проверка реализации ансамбля — 2026-10-18

Полный локальный набор после исправления обработки событий в пакетном Qwen: **366 тестов пройдены** (`python -m pytest -q -p no:cacheprovider`, 52.20 s). Одно предупреждение об устаревающей интеграции httpx/Starlette относится к существующему веб-приложению. Проверка кода не является измерением точности банковского детектора или скорости полного Qwen 8B на L40S.

Проверены последовательное декодирование, перекрытия и конец видео, сохранение пропорций, контроль SHA, возобновление и отказ при изменённом кэше, ошибки моделей, прекращение по таймауту, защита исходного видео и коэффициентов от перезаписи. Для ролей проверены сохранение связи с тем же ID после выхода из настроенной зоны, момент установления роли, отсутствие использования будущих наблюдений и сброс между видео. После восстановления пропущенного окна последующие результаты Qwen пересчитываются с новым контекстом.

Обучение проверено на синтетических числовых данных: пять внешних разбиений, три внутренних разбиения для обучения объединения, нормализация только на обучении, выбор порога только на калибровке, неизменность обученных параметров при изменении тестовых меток, сохранение/загрузка JSON с численным совпадением sklearn. Проверено, что правильный бинарный ответ с неверным окном не засчитывается как успешная локализация.

## Реальные модели и декодирование

| Проверка | Результат | Практическая граница |
|---|---|---|
| Все исходные MOV, после объединения точных дубликатов | 40 уникальных видео, 38 908 / 38 908 кадров декодированы; все запланированные времена внутри окон | Проверка чтения файлов и времени, модели не запускались |
| YOLO11n + ByteTrack, закреплённые полные веса | Синтетическое видео 2 s: 40 кадров прочитано, 8 выбрано, 2 окна; GPU запуск успешен | В видео только движущийся прямоугольник, качество поиска людей не измерено |
| Native ByteTrack + LAP | Один ID сохранён на четырёх синтетических наблюдениях прямоугольника | Проверка механизма сопоставления, не устойчивость на кассовых видео |
| X-CLIP, закреплённые полные веса | SHA-256 совпал; 2 окна, по 2048 признаков, 4 прохода для кадра и кропа; все переданные выборки покрыты | Не проверка классификации нарушений |
| Qwen3-VL, маленькая модель той же архитектуры | Настоящий локальный процессор, изображения, forward и generation; бинарные оценки совпали с полным выходным слоем | Полные веса Qwen 8B не запускались на локальной GPU |

Для полных YOLO и X-CLIP соединения сокета были заблокированы на время загрузки модели и обработки: попыток сетевого обращения не было. Публичные веса предварительно скачаны отдельно. Исходные банковские кадры для этих GPU-проверок не использовались и не передавались внешним моделям.

Среда GPU-проверки: Windows, RTX 5050 Laptop 8 GB, PyTorch 2.8.0+cu128, Transformers 4.57.6. На синтетическом двухсекундном примере X-CLIP занял 5.27 s с пиком выделенной памяти 0.767 GiB; YOLO-проход — 7.41 s. Эти числа включают конкретный локальный запуск и **не оценивают** скорость полного ансамбля или 145-секундного видео на L40S. Серверная установка закрепляет PyTorch 2.6.0+cu124; её совместный запуск проверяется отдельно на Brev.

## Пакетная версия Qwen

Добавлены `qwen_batched.py`, `run_batched.py` и локальное сравнение `benchmark_qwen.py`. В одном окне два запроса оценок выполняются одним batch=2, два запроса наблюдений — вторым. Количество выбранных кадров, тексты запросов, ограничения JSON и память не сокращены. Серверный запуск `run.py` и пять файлов его fingerprint сохранены без изменений; его текущие результаты продолжают быть совместимыми.

На настоящем локальном процессоре Qwen и маленькой модели нативной архитектуры проверены разные длины запросов, левое дополнение, разное количество/размеры изображений и их соответствие отдельным специалистам. Пакетные бинарные оценки совпали с последовательными в допуске 0.000002 на CPU и 0.004 при BF16 на CUDA; три сгенерированных токена совпали. Это проверка механизма, не доказательство полного совпадения ответов предобученной 8B. Проверены раздельные схемы наблюдений, кропы, память, ошибки/OOM, собственное возобновление и запрет старого кэша Qwen. `predict.py` выбирает старый или пакетный backend по сохранённому протоколу.

На синтетическом видео с настоящим декодированием проверены перенос media/X-CLIP, независимость копий и побайтовая неизменность исходного кэша, повреждённые кадры/признаки, несовпадающие протоколы, завершение после ошибки и пометка исторических таймеров при возобновлении. Отдельная проверка benchmark подтверждает общую копию модели, чередование порядка, защиту существующих файлов и отсутствие текста наблюдений в отчёте.

Из предоставленных пользователем логов L40S: ролики 2–4 заняли соответственно 90.98, 69.11 и 215.48 s на 2, 2 и 6 окон. Это примерно 37.6 s на окно после первоначальной загрузки; данные получены со скриншотов, независимый доступ к серверу не использовался. На отдельном снимке `nvidia-smi` GPU загружен на 100%, занято 20715 из 46068 MiB. Эти показания не подтверждают отсутствие других процессов и не измеряют весь набор.

Затем пользователь запустил сравнение на L40S: медиана двух последовательных запусков 29.1209 s, двух пакетных 25.2908 s, отношение 1.1514 (примерно на 13.2% меньше времени). Пик выделенной PyTorch памяти — около 17.82 и 19.33 GiB соответственно. Из 25.29 s пакетного окна около 23.05 s заняла генерация наблюдений. Это один фрагмент и пустая предыдущая память; замер не доказывает соблюдение лимита 300 s на полном видео.

У обоих режимов в этом замере наблюдения получили `invalid_json_or_schema`. Их содержательное совпадение не доказано: сравнивались бы запасные пустые структуры. Теперь benchmark выдаёт `observations_equal: null`, если хотя бы одна схема не принята. Добавлена отдельная команда `diagnose_qwen.py`, которая сохраняет только фиксированные коды отказа проверки и структурные сведения, включая диагностическую проверку единственного внешнего Markdown-блока. Проверка ограждений служит только диагностикой и не меняет принятие наблюдений.

Последующая серверная диагностика пользователя вернула `invalid_event_list` для обоих специалистов, длину ответов 1094 и 1093 символа, без Markdown-ограждений. Старый код использует этот отказ и для неверного типа `events`, и для списка длиннее восьми; конкретный тип и размер в том отчёте не были сохранены, поэтому ни одна из двух причин отдельно ещё не подтверждена.

В `observations_v2` корректный список до 64 событий сохраняется целиком; каждое событие проверяется прежним строгим валидатором блоками до восьми элементов. Один объект с точными полями события приводится к одноэлементному списку. Произвольные словари, `null`, неверные ID/таймкоды и лишние поля отклоняются. Память следующего окна остаётся ограничена восемью событиями. Новый протокол `forte_specialists_batched_v2` включает хеш схемы, не смешивается с прежними результатами и сохраняет совместимость исходного последовательного кэша со своим кодом.

Проверены сохранение 9 и 64 событий, отклонение неверного девятого элемента, полный список кадров-кандидатов, повторное чтение расширенного кэша и ограниченная память. Диагностика теперь выдаёт `events_type`, `event_list_count`, `accepted_event_count`, без значений событий. Флаг `--require-valid` возвращает ненулевой код после сохранения отчёта, если один из двух специалистов не прошёл проверку; условное продолжение через `&&` проверено. Исправление ещё нужно проверить на полном Qwen 8B на сервере; `valid` подтверждает схему, а не истинность наблюдений.

## Ещё не измерено

Точность, precision, recall, ложные тревоги, пропуски и попадания в размеченные интервалы нового ансамбля на исходном наборе. Для этого нужно запустить `run.py`, затем `fusion.py` и получить `results/fusion-v1/summary.json`.

Также не измерены полный прогон нового ансамбля на L40S, успешное завершение полного видео в 300 секунд, устойчивость к новому ракурсу и неизвестным нарушениям. Не проверены точные моменты событий, нормативные основания и конечный API жюри. Предсказания остаются экспериментальными; обещаний 85%+ или безошибочной работы нет.
